## Required before any production change
1. Request the **renewed wildcard/server (leaf) PEM certificate** from the client/issuer, issued for `*.resustainability.com` (and optionally `resustainability.com`). Do not accept a CA-only bundle or rename the CA file as a server certificate. Ask the client to transfer the leaf securely; never send or commit the private key to the app repository.
2. With the server operator, inspect `sudo nginx -T` and identify the `server_name vms.resustainability.com` HTTPS block, its `ssl_certificate` and `ssl_certificate_key` paths, and whether TLS terminates on this host, a proxy, or a load balancer. Confirm whether other hostnames share the same paths/certificate and whether Certbot owns these files (`sudo certbot certificates` and relevant renewal hooks). **Do not edit/restart anything at this stage.**
3. Offline, check the renewed leaf: `openssl x509 -in renewed-leaf.pem -noout -subject -issuer -dates -ext subjectAltName -ext basicConstraints`; match SHA-256 of DER public keys from `openssl x509 -in renewed-leaf.pem -pubkey -noout | openssl pkey -pubin -outform DER | openssl dgst -sha256` and `openssl pkey -in star_resustainability.com_2026.key -pubout -outform DER | openssl dgst -sha256`. Values **must match**. Verify `openssl verify -purpose sslserver -verify_hostname vms.resustainability.com -CAfile 'DigiCert Global Root G2.pem' -untrusted 'RapidSSL TLS RSA CA G1.pem' renewed-leaf.pem` returns OK, and confirm certificate validity dates include deployment time. If any check fails, stop and request the correct leaf/key/chain.

## Change procedure (only after all checks pass and the server owner authorizes it)
1. Back up the active Nginx site and its existing certificate/key files outside the repository. Protect the new key (`root` ownership, mode `0600`; restrict certificate directory access). Preserve any working Certbot renewal configuration; if Certbot manages the active paths, arrange a compatible replacement/renewal method rather than overwriting its live files blindly.
2. Build the Nginx full chain **in this exact order**: renewed leaf PEM, then `RapidSSL TLS RSA CA G1.pem`. Do **not** prepend the CA or include the self-signed `DigiCert Global Root G2.pem` in the served chain. Set the active HTTPS site's `ssl_certificate` to this fullchain file and `ssl_certificate_key` to the matching private key. Apply the change wherever the verified live TLS terminator serves `vms.resustainability.com`; do not assume this repository's port-80 templates are the live HTTPS configuration. Leave the app/login code untouched.
3. Run `sudo nginx -t` before a graceful `sudo systemctl reload nginx` (not a restart). If the terminator is not Nginx, use its documented certificate replacement and validation procedure instead. No reload/change is authorized by this plan alone.
4. After reloading, verify from outside: `openssl s_client -connect vms.resustainability.com:443 -servername vms.resustainability.com -showcerts -verify_return_error </dev/null`, `curl -Iv https://vms.resustainability.com/auth`, certificate expiry/SAN and intermediate chain. Repeat for every hostname using the same certificate; then test login with an authorized real account. If validation fails, restore the backed-up config/files, `nginx -t`, and gracefully reload to roll back. Do not mistake an invalid-credentials response for a successful login.
